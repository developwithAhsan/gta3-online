How re3 Runs in a Browser with WebAssembly

Updated 20267 min read

Running a native-style game engine in a browser requires more than compiling C++ to WebAssembly. The browser has different rules for files, graphics, input and persistence, so the launcher provides a compatibility layer around the re3 engine.

WebAssembly and Emscripten

Emscripten compiles the C/C++ project to a WebAssembly module plus JavaScript glue code. The JavaScript creates the module, connects the HTML canvas and exposes selected runtime methods such as the virtual filesystem and main entry point.

MEMFS for live game files

The current runtime expects normal filesystem-style paths. Emscripten MEMFS provides those paths inside the WebAssembly environment. Files extracted from the ZIP become available under the configured game root before re3 starts.

OPFS for persistent archive storage

MEMFS is session memory, so it disappears after the page closes. OPFS solves a different problem: it can keep the compressed source archive in browser storage across visits. On the next launch the browser reads that local archive and rebuilds the runtime filesystem without another full network download.

Diagnostics and frame timing

The launcher exposes engine boot stages, input state and frame timing so black screens or startup stalls are easier to diagnose. The runtime also resizes the canvas when the browser viewport or fullscreen state changes.

Why this architecture is useful

It separates persistent storage from the live engine filesystem. That avoids making the entire game directory an IndexedDB synchronization job while still keeping the expensive network archive cached locally.
